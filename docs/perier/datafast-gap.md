# DataFast vs OpenAnalytics: gap report

Written 2026-11-13. OpenAnalytics (OA) is our fork at v0.8.0 (commit `b572a5e`), read at `/Volumes/PlanckSSD/code/projects/openanalytics`. DataFast was read from its public site, docs (`.md` versions), `llms.txt`, changelog and pricing, all accessed 2026-11-13. No DataFast account was used, so dashboard-only behaviour comes from DataFast's own docs and changelog, not from use.

Use case this is ranked for: BetterBahn (German train fares) runs OA. It sells Stripe Pro subscriptions (€6.99/month, €39.99/year) and a one-off €3.99 Trip Pass. Checkout sets `client_reference_id = user.id` (`betterbahn/apps/web/src/app/api/subscribe/route.ts:416,588`), and the web app calls `oa.identify` (`betterbahn/apps/web/src/lib/analytics.ts`). The immediate questions are: which pages, sources and in-product moments lead to paid conversion, and what are the funnel results and custom-event counts, read over MCP.

Status key: **Yes** = OA has it. **Partial** = some of it, or only on one surface. **No** = absent. **Ahead** = OA does more than DataFast. **Unverified** = could not be confirmed from primary sources.

## 2. Gaps ranked by value for BetterBahn

Effort: **S** ≈ a day or two, **M** ≈ a week, **L** = several weeks. All estimates are rough and unverified against the test suites.

1. **Custom-event counts on `/v1/read` and MCP** — S.
   The route and service already exist (`service.customEvents`, `apps/api/src/http/analytics.ts:428-460`). Mount `GET /read/analytics/custom-events` in `apps/api/src/http/read-key.ts` (next to `report('sources'…)`, ~line 940, keeping the label decoration via `listEventDisplayNames`), then add a `custom_events` row to `mcpTools` in `apps/api/src/http/mcp.ts` and to the roster pinned in `tests/unit/mcp-write-tools.test.ts`. Also update `apps/web/app/docs/api/page.tsx` and the contracts OpenAPI document (`packages/contracts`).

2. **Funnel results on `/v1/read` and MCP** — S.
   Mount `GET /read/analytics/funnel` (ad-hoc `steps=` plus `scope`/`window_ms`), plus a `funnel_id` form that loads a saved funnel from Postgres (`apps/api/src/http/funnels.ts`) and runs `service.funnel`. Add `funnel_results` to `mcp.ts`. Keep the 92-day cap and the cost gate.

3. **Revenue and conversions by source, campaign and entry page** — M.
   The data is already per charge in `revenue_attributions` (`ft_*`/`lt_*` referrer, UTMs, entry page). Add a gateway operation in `apps/query-gateway/src/operations.ts` that groups converted charges by a chosen touch (first or last) and dimension, returning revenue, order count and buyers. Add a service method (`apps/api/src/analytics/service.ts`), an owner-only route in `apps/api/src/http/revenue-analytics.ts`, an aggregate `/read/revenue/attribution` in `read-key.ts` (aggregates only, so it fits ADR-0049's rule), an MCP tool, and a "Revenue by source / entry page" card on `apps/web/app/dashboard/[site]/revenue`. Joining visitors from the sources report would give conversion rate and revenue per visitor per source.

4. **Which in-product moments precede paid conversion** — M.
   This means a "custom events before purchase" breakdown: for attributed charges, count the custom events in the journey before `occurred_at` (e.g. `paywall_viewed`, `price_alert_created`, `split_found`, `ben_chat`). The journey sessions already exist (`analytics.revenue_transaction_journey`). Event-level membership needs `events_raw` keyed by the same identity, so add a bounded operation in `operations.ts`, a route in `revenue-analytics.ts` and an MCP tool. DataFast covers this with `filter_goal` plus journeys; OA's version can stay aggregate-only.

5. **Attribution that survives the daily ID rotation before sign-up** — M.
   Today first touch before `identify` reaches back only to the last UTC midnight (`revenue-attribution.ts` `identity_scope` note). Someone who finds BB via Google on Monday and buys Pro on Wednesday is credited to Wednesday's session. One option within OA's model: an opt-in per-site "first-touch hint". The tracker stores the first acquisition source (referrer domain, UTMs, entry path, date; no ID) in first-party storage and attaches it to `identify`/`conversion`, gated like the existing linking hints (ADR-0064 D4a in `apps/tracker/src/privacy.ts` and `core.ts`). `touchpointsFor` in `packages/domain/src/revenue-attribution.ts` would then prefer it, with a new `matched_via`/scope value. This is a privacy decision before it is code; it needs an ADR and a privacy-notice line on BB.

Add a rollup keyed `(event_name, property_key, property_value)` with a cardinality cap (ClickHouse migration under `packages/clickhouse`, worker rollup in `apps/worker/src/ingest`), an operation in `operations.ts`, a route next to `custom-events`, and an MCP tool. ## 3. Where OA is ahead

- Self-hosted under AGPL, cookieless by default, DNT/GPC honoured at the collector, consent gating, and a signed query gateway (README).
- Dashboard-defined, versioned no-code events with publish and rollback, available over MCP (`event-definitions.ts`).
- Web vitals (`vitals.ts`, `web-vitals-card.tsx`).
- Revenue accounting: refunds, disputes, fees and net in integer minor units. Attribution states its confidence and identity scope, and stores both first and last touch.
- Paid click IDs recover the ad source when the referrer is stripped (`click-id.ts`).
- Imports from Plausible and Umami; CSV/JSON exports.
- MCP write tools for sites, funnels, event definitions, widgets and sharing, with read-only annotations; reads go through one cost-gated path (`mcp.ts` header).
